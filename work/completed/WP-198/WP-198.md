# WP-198 — The first capture reads pacman.log as a stream

0.2.0 if it fits, else 0.2.x. From the review of WP-119 (2026-10-10, N1):
WP-119 puts the 90-day look-back on the default path, so the first
capture now always reads the whole package log.

Role: Engine Dev. Small–medium. Reviewer: Opus; Fable stage 2 (engine core,
idempotency).

**Problem.** The pacman collector reads `/var/log/pacman.log` into memory
whole on a first capture. A synthetic 240 MB log took 60.6 s and 2.4 GB
RSS (debug build); a busy real 90-day log (40 000 events) took 15 s and
147 MB. Long-lived Arch installs have logs of hundreds of MB.

**Do.**

- Read the log line by line (buffered), from the cursor or from the
  look-back start; never hold the whole file. Keep the existing inode and
  offset cursor semantics.
- For the look-back, find the 90-day start without parsing every older
  line in full (timestamps are ordered: skip cheaply, or seek from the
  end if the format allows it safely).
- Bounded memory: a test with a large synthetic log (generated in a temp
  dir on disk, not committed) asserts peak RSS and time stay within a
  stated budget, with a time limit on the test itself.
- Idempotency unchanged: a second capture writes nothing (existing tests
  plus one on the large log).
- SPEC-ENGINE §4 pacman; CHANGELOG.

**Acceptance.** The tests; `just check` green; `just check-rss` not worse.
AGENTS.md §5 evidence words in the handover.
