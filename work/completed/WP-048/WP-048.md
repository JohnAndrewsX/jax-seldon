# WP-048 — Repository hygiene: community files, templates, topics, release notes from CHANGELOG, cargo audit

## Goal
The public repository meets GitHub's community standards and the
release process documents itself: contributors know how to help, users
know how to report a vulnerability, issues arrive in a usable shape,
release notes come from the CHANGELOG, and dependency advisories are
checked in CI.

## Inputs
README.md, CHANGELOG.md, LICENSE, .github/workflows/{ci,release}.yml,
packaging/README.md, AGENTS.md §2 (English), §8 (safety), docs/TESTING.md,
GitHub community profile checklist (read-only), engine/Cargo.lock.

## Outputs
- `CONTRIBUTING.md`: how to build and test (`just check`), the worktree
  and work-package flow in two paragraphs, commit style, English-only
  rule, how specs and ADRs are changed, review expectations.
- `SECURITY.md`: supported versions, how to report (GitHub private
  vulnerability reporting enabled via `gh` if available, else the
  maintainer address from the PKGBUILD), what is in scope (the engine
  runs as the user, no network; the plugin runs unsandboxed in the
  shell).
- `CODE_OF_CONDUCT.md` (Contributor Covenant 2.1, unchanged text).
- `.github/ISSUE_TEMPLATE/{bug_report,feature_request}.yml` (forms with
  `seldon doctor` output and `seldon --version --json` requested) and
  `.github/PULL_REQUEST_TEMPLATE.md` (checklist: `just check`, specs,
  CHANGELOG line).
- Repository metadata via `gh repo edit`: topics (`omarchy`, `arch-linux`,
  `hyprland`, `quickshell`, `rust`, `obsidian`, `flight-recorder`),
  homepage (the repo's docs path until a site exists); the same for
  `jax-seldon-plugin` (description already set).
- Release notes: the `release` job takes the matching `## [X.Y.Z]`
  section from CHANGELOG.md as the release body (fails the job when the
  section is missing, so a tag without notes cannot ship).
- CI: `cargo audit` (via `rustsec/audit-check` or `cargo install
  cargo-audit` in the Arch container) as a non-blocking advisory job
  first; a note in CONTRIBUTING on when it becomes blocking.
- `docs/VERSIONING.md`: SemVer for the engine and plugin, how
  `contractVersion` relates (a contract bump is a minor at least), the
  tag flow, what `CHANGELOG.md` must contain before a tag.
- A CHANGELOG `[Unreleased]` entry for all of this.

## Acceptance tests
- `just check` exit 0; YAML lint of the new workflow parts.
- GitHub community profile shows every item green (description, README,
  CoC, contributing, license, security policy, issue templates).
- Dry run of the release workflow shows the notes extraction working on
  `0.1.0`.

## Constraints
Text files and workflow only; no engine or plugin code; no secrets;
English; a guard block is reported, never worked around.
