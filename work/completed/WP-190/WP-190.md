# WP-190 — CI runs the plugin's checks, stage 1: node tests and Omarchy's validator

0.2.0, **before the tag**. Origin: study of Tom Ballard's Omarchy work
(2026-10-09, `jax-seldon-private/study-tcballard/`), operator decision E66
(stage 1). Stage 2 (Quickshell in CI) is WP-191. Ideas only, no code taken.

Role: QA / Scaffold (Opus). Small. Reviewer: Opus; Fable stage 2 only for
the `release.yml` step (release workflow). No ADR.

**Problem.** CI runs none of the plugin's checks. The container installs
`git rust just jq shellcheck rsync` (`.github/workflows/ci.yml:30`), and
`SELDON_SKIP_HOST_CHECKS=1` skips `plugin-validate`, `qmllint` and the whole
`plugin-test` recipe (`justfile:181-250`), including the pure-JS
`node tests/plugin/model.test.js`. A PR that breaks `Model.js` or the
manifest is green in CI. `docs/TESTING.md:364` says the validator needs the
omarchy CLI; it is 118 lines of bash and jq with no other dependency
(`$OMARCHY_PATH/bin/omarchy-plugin-validate`).

**Goal.** A PR that breaks the plugin's logic or its manifest turns CI red;
the plugin the store installs (the subtree split) is validated before the
release pushes it. The dev host and the test host stay the gate for
behaviour (AGENTS.md §1, "code is truth").

**Do.**
- `ci.yml`: add `nodejs` to the pacman line; update the header comment
  (what runs, what does not).
- `justfile`: split the skip by need. Under `SELDON_SKIP_HOST_CHECKS` the
  node and bash parts run: `node tests/plugin/model.test.js`,
  `bash tests/plugin/terminal-scripts.sh`,
  `bash tests/plugin/real-home-guard.test.sh`; only the Quickshell
  harnesses, `qmllint` and `check-tokens.py` (they need the shell tree)
  stay host-only. Decide `model.bench.js` on a CI runner's timing: run it
  with a CI budget or keep it host-only, and say which.
- `packaging/omarchy-pin`: one 40-hex `omacom/omarchy` commit (the
  study's name for the upstream repository; verify it) and the sha256 of
  `bin/omarchy-plugin-validate` at that commit, with the Omarchy version
  as a comment. Pick the commit whose validator equals the one installed
  on the test host (`omarchy version`); `packaging/README.md` says how to
  refresh the pin (as for the action pins).
- `plugin-validate`: when the omarchy CLI is absent (CI), fetch the pinned
  file over HTTPS, check its sha256, refuse on mismatch, run it on
  `plugin/`. On the dev host the installed `omarchy plugin validate`
  stays.
- `release.yml`, build job: run the same pinned validator on the exact
  split (`git subtree split --prefix=plugin`, then `git archive | tar -x`
  into a scratch dir) before any push; `tests/release/workflow-pins.test.sh`
  asserts the step (unconditional, before `Summary`, no `continue-on-error`).
- `docs/TESTING.md`: the table row (`:22`) and `:364` corrected; a short
  "what CI runs" list.
- No Quickshell, no `$OMARCHY_PATH/shell` checkout in this WP (WP-191).

**Acceptance.** In a throwaway branch: a mutant that breaks a `Model.js`
function turns CI red (CI); a manifest with a missing entry point turns CI
red (CI); a wrong sha256 in `packaging/omarchy-pin` makes `plugin-validate`
refuse (fixture, CI); a release dry run (`workflow_dispatch`) validates the
split (CI); `just check` on the dev host unchanged and green (fixture,
headless). The handover links the red and green runs.

**Inputs.** AGENTS.md §1, §5, §7 (plugin rules); `.github/workflows/ci.yml`,
`release.yml`; `justfile` (`plugin-validate`, `qmllint`, `plugin-test`);
