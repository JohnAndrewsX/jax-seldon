# WP-173 — A held key never confirms

0.2.0, before the tag. Found by the devil's advocate of the prototype
debate (group 1, 2026-10-09), confirmed by the orchestrator on `next`.

Role: Plugin Dev. Small. Reviewer: Opus (safety: Fable stage 2 short).

**Problem.** Writing actions on the desk arm on the first press and run
on the second (SPEC-PLUGIN §5, `plugin/components/desk/Arm.qml`). The
desk's key handler (`plugin/Desk.qml`, `keyCatcher` `Keys.onPressed`)
does not look at `event.isAutoRepeat`. Omarchy sets Hyprland
`repeat_delay = 250`, `repeat_rate = 40`
(`$OMARCHY_PATH/default/hypr/input.lua`), so holding a key for a quarter
second sends a second press of the same key: the action arms and runs.
Holding `x` drops a case ("This is final"); holding `a` starts an agent.

**Do.**

- An auto-repeated key event never confirms an armed action and never
  arms one. Navigation keys (j/k, arrows, page keys) keep repeating.
- Put the rule in one place (`Arm.press` takes the event's repeat flag,
  or the handler filters before `root.key`), so every section and the
  action bar's keyboard path follow it; a mouse click is unaffected.
- The armed hint stays visible while the key is held; releasing and
  pressing again confirms as before.
- Tests in `tests/plugin/` (the desk key harness): for every writing
  action key, a press followed by auto-repeat events of the same key
  leaves the action armed and not run; a real second press runs it;
  j/k repeat still moves the selection.
- SPEC-PLUGIN §5: one sentence ("a held key does not confirm").
- CHANGELOG.

**Acceptance.** The tests above; `omarchy plugin validate plugin/` and
`qmllint` clean; `just check` green. A live check on the test host:
hold `x` on a queued case for two seconds → armed, not dropped.

**Inputs.** plugin/Desk.qml, plugin/components/desk/Arm.qml, every
caller of `arm.press`, docs/SPEC-PLUGIN.md §5, tests/plugin/,
`$OMARCHY_PATH/default/hypr/input.lua`, the omarchy skill.
