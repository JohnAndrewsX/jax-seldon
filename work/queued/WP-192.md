# WP-192 — A recorded live test per release (0.2.0: the record; 0.3: the tag refusal)

Part 1 0.2.0, **before WP-126's live check**; part 2 0.3, built inside
WP-188. Origin: study of Tom Ballard's Omarchy work (2026-10-09,
`jax-seldon-private/study-tcballard/`), operator decision E67. Ideas only,
no code taken.

Role: Scaffold (Opus). Small. Reviewer: Opus; Fable stage 2 (release
process). No ADR.

**Problem.** "The tag waits for the fresh-host live test" (operator
decision 2026-10-06) is a convention. Nothing records which commit was
tested live, on which Omarchy version, with which scenarios and counts;
for 0.1.4 the tag carried 40 changed lines of `plugin/BarWidget.qml` and
guard scripts after the tested commit (study, judgement table).

**Goal.** Every release from 0.2.0 has one machine-readable record of its
live test, bound to a commit; from 0.3 the release workflow refuses a tag
whose code changed after that commit.

**Do (part 1, 0.2.0).**
- Format, documented in `docs/VERSIONING.md` ("Release acceptance record")
  and pointed to from `docs/TESTING.md`: `packaging/acceptance/vX.Y.Z.json`
  with `version`, `status` (`passed` | `failed` | `partial`), `commit`
  (40 hex, the commit deployed to the test host), `date`, `omarchy`
  (`omarchy version`, `omarchy version channel`), `engine` and `plugin`
  versions as installed, `scenarios` (id, title, `where` — one of the
  AGENTS.md §5 evidence words — `result` `passed` | `failed` | `not run`,
  `counts` per ADR-0027 §1, short notes) and `limitations`. No hostnames,
  user names or private paths (AGENTS.md §8).
- Rules: `status: passed` only when every scenario is `passed`; a scenario
  `not run` makes the record `partial` and is listed in `limitations`.
- `packaging/acceptance-check.sh X.Y.Z [REF]` (bash + jq, no network):
  checks the fields and rules, that `commit` is an ancestor of `REF`
  (default `HEAD`), and that `git diff --name-only <commit> <REF>` touches
  only `docs/`, `*.md`, `work/` and `packaging/acceptance/`; prints each
  offending path. Exit 0 ok, 1 refused.
- `tests/release/acceptance-check.test.sh` in `check-packaging`: a good
  record, each broken field, a `not run` scenario under `passed`, a code
  change after the commit, a commit that is not an ancestor — each a
  failing case run against a scratch git repository.
- `scripts/deploy-test-host.sh` prints the deployed commit in the form the
  record needs (if it does not already).
- The orchestrator's tag question for 0.2.0 quotes the checker's output;
  `release.yml` is not changed in part 1.

**Do (part 2, 0.3 — done in WP-188, see its study section).** The build
job, on tag push only, runs the checker against the tag and refuses
without a `passed` record; `workflow_dispatch` dry runs report only;
`tests/release/workflow-pins.test.sh` asserts the step.

**Acceptance (part 1).** `acceptance-check.test.sh` green with every
failing case proved (fixture, CI); the format documented; WP-126 writes
`packaging/acceptance/v0.2.0.json` with it and the checker passes on the
release commit (test host for the scenarios, fixture for the check).

**Inputs.** AGENTS.md §5, §8; `docs/VERSIONING.md`, `docs/TESTING.md`
