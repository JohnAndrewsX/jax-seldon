# WP-158 — The lock test can fail while other tests spawn processes

Ships in 0.2.x (a test robustness fix; no behaviour change expected).

Role: Engine Dev (Opus, medium). Small.

**Observed.** `logbook::lock::tests::second_lock_is_refused_until_release`
failed once in gate-124b (2026-10-08 02:4x, a loaded host):
`assertion failed: acquire(&path).is_ok()` after `drop(first)`. A likely
cause is a child that another parallel lib test forked between `open` and
`exec` (the WP-136 git runner tests spawn with process groups). Such a
child briefly holds a copy of the lock's file description, so the flock
outlives the drop.

**Do.**
- Confirm the cause.
- Make the lock robust against inherited descriptors, if the engine itself
  can hit this (for example `seldon` spawning git while holding the lock):
  O_CLOEXEC is already Rust's default, so check the fork/exec window and
  `posix_spawn`.
- Make the test deterministic: run it in its own process, or use a short
  retry for the re-acquire.
- Say whether production code can hit the same window, and fix that if
  so.

**Acceptance.** 200 runs of the lib tests in a loop under load, with no
failure.
